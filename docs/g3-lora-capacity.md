# 原版调度的 LoRA 名额容量对照

固定保护阈值无法稳定同时改善冷门尾部与热门排队。这组对照检查增加一个活跃 LoRA 名额的效果。使用同一 B0 原版准入，分别设 `max_loras=2` 和 `max_loras=3`，并发请求上限保持 8。两档共用 BF16 模型、适配器、GPU 显存利用率参数、预热、负载和 SLO。实验改变的资源是允许同时活跃的适配器种类数。

沿用 5 秒实验的三个种子及突发请求轨迹。每个种子重启服务并在两档交替运行顺序。调度进程在启动时记录实际容量，分析器也从准入事件核对是否真的用到第三种 LoRA。以重新实测的两名额 B0 为基线，继续检查冷门 P95 是否下降至少 20%、热门 P95 增加是否不超过 1 秒、Goodput 降幅是否不超过 5%。

显存同时记录 vLLM 启动探测得到的可用 KV 容量、KV token 容量和 nvidia-smi 的整卡粗采样。两档预留相同的显存利用率比例，整卡峰值可能接近。KV 容量变化能补充说明名额增加是否挤占 KV 预算。两个指标都无法单独识别 LoRA 权重或算子工作区的物理占用。

```bash
~/work/vllm-lora-admission/.venv/bin/python -m bench.run_g3 \
  results/g3/lora-capacity-replay --config configs/g3-lora-capacity.json
python3 -m bench.analyze_g3 results/g3/lora-capacity-replay
python3 -m bench.analyze_capacity results/g3/lora-capacity-replay
python -m bench.plot_g3 results/g3/lora-capacity-replay
```

## 结果

三组配对共 288 条请求，全部在 36 秒窗口内完成，无超时、未准入或抢占。三名额组均实际使用第三种 LoRA，日志中共有 18 次由两种活跃适配器增至三种的准入，C、D 各 9 次。

| 种子 | C/D 合并排队 P95，2 → 3 | 冷门 P95 降幅 | 热门 P95 变化 | Goodput 变化 |
|---:|---:|---:|---:|---:|
| 8167 | 9.27 → 5.55 s | 40.2% | −1.87 s | 0% |
| 9283 | 8.68 → 5.66 s | 34.8% | −0.10 s | 0% |
| 10313 | 8.32 → 6.11 s | 26.5% | +0.39 s | 0% |

三组同时达到预设三项门槛。冷门 P95 的配对中位减少 3.02 秒，相对降幅中位数为 34.8%。每个运行有 24 条请求达到 SLO，Goodput 均为 0.667 条/秒。Qwen3 模型与生成 token 上限相同，以计划发包起点到最后完成作为忙时窗口，三对实际输出速率分别变化 115.7 → 124.6、123.5 → 127.8、119.8 → 124.2 token/s。

以 8167 的第二波 C 为例，两名额时 C 排队 9.28 秒，准入时 A/B 都已退出。三名额时 C 排队 4.02 秒，准入时 A 和 B 仍然活跃。D 在随后重新空出的种类名额上准入。仍有 8 条并发请求上限，四种 LoRA 共用三个名额。两名额组在该种子的第 2、3 波有约 0.48 秒请求重叠，较晚发出的 C/D 可复用上波仍活跃的种类，因此总体改善不能理解为每条冷门请求都更快。

三组的启动 KV 容量均由 43,904 降为 43,808 token，减少 96 个约占 0.22%。启动探测的可用空间由 4.69 降到 4.68 GiB。在整卡采样中，三名额相对两名额的峰值差为 +90、−30、+320 MiB，受桌面进程和采样影响，适合保留原数而非归为 LoRA 的固定额外显存。

对于本次小模型与四种适配器的突发负载，资源允许时优先考虑增加一个种类名额。结论以同策略、同轨迹的容量对照为依据。此前 B3 测试是不同运行时段的历史结果，若要判断三名额 B0 与两名额 B3 的优劣，需要直接配对。逐次准入、启动资源和配对明细位于 `results/g3/lora-capacity-01/`。
