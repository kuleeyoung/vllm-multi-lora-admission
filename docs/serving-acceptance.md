# 选项 A 连续运行与回退验收

当前启动和绑定检查验证了三名额推荐档与两名额回退档。本轮直接调用实际服务入口，检查同一进程承受多轮负载、关闭并按回退档重启的行为。

推荐档在同一个 API 进程和 EngineCore 上跑三轮，每轮先发送两次 A/B 主导的突发流量，再发送持续流量。突发窗口 32 条、持续窗口 14 条。回退档使用同一条突发轨迹和持续轨迹各一次。请求来自固定 seed 18919，服务上限八条。各窗口最多 24 秒，使用 TTFT ≤ 2 秒、TPOT ≤ 120 ms 记录达标吞吐。

通过条件包括：启动参数匹配所选档位，`/v1/models` 注册基础模型与 A/B/C/D，请求成功并在窗口内完成，流式返回 ID、模型名和 token 计数一致，轮间健康检查通过，换档关闭旧 EngineCore。模型名与请求 ID 的核对用于检查响应路由，权重绑定的数值效果已在 [配置落地验证](serving-option-a.md) 单独核验。

保留逐请求结果和运行中 GPU 采样，并在启动及每轮完成后记录整卡显存、API 进程 RSS 和 EngineCore RSS。短时采样可观察这一轮资源变化。判定长期稳定性还需要更长的时间跨度和更多空闲采样。

在 WSL 项目目录复跑，输出目录需为新目录。

```bash
python3 -m bench.validate_serving results/serving/option-a-acceptance-replay
```

## 结果

推荐档在同一个 API/EngineCore 上连续完成三轮，138 条请求全部成功。从启动后采样到第三轮结束约 78 秒。随后关停推荐档，按两名额回退入口重新启动，新进程完成同轨迹的 46 条请求。八个窗口共 184 条全部在时间窗内完成，请求 ID、模型标签、token ID 数和服务 usage 一致。启动日志确认了 3/2 个 LoRA 名额与两档 8 条并发请求上限。两种场景各自的计划轨迹哈希跨档位一致。

| 模式与场景 | 完成数/轮 | 达标数/轮 | TTFT P95 | TPOT P95 |
|---|---:|---:|---:|---:|
| 推荐档突发，3 轮 | 32 | 16 | 3.43–3.96 s | 45.7–54.0 ms |
| 推荐档持续，3 轮 | 14 | 12 | 3.18–3.52 s | 44.5–48.7 ms |
| 回退档突发，1 轮 | 32 | 16 | 6.06 s | 51.2 ms |
| 回退档持续，1 轮 | 14 | 8 | 5.00 s | 44.8 ms |

本表用于连续运行验收。回退档每类只有一轮，且在独立进程中后运行。选型效果仍以 [同轮配对](g3-strategy-decision.md) 为准。

推荐档的 EngineCore RSS 首轮后比启动时增加约 213 MiB，之后两轮合计增加 84 KiB。三次轮间整卡显存采样为 9,619、9,616、9,612 MiB。两档关闭后旧 EngineCore 进程消失，端口 8018 无监听。两份日志均保留 Python 资源跟踪器在退出时报告 1 个 semaphore 的警告。短时资源采样与进程退出证据不足以判定该警告是否会在长期运行中造成问题。

配置、各窗口结果、资源采样和启动日志位于 `results/serving/option-a-acceptance-01/`。整包快照为 `results/archive/vllm-multi-lora-2026-11-18-serving-acceptance.zip`。
