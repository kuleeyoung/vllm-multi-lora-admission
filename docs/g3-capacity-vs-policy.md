# 三名额原版与两名额 B3 直接比较

容量对照已经证明原版 B0 多一个名额可改善同一组突发请求。此前 B3 的结果来自另一批运行。这里新选 11443、12611、13723 三个种子，直接配对两套可用配置。B3-5s 使用两个活跃 LoRA 名额，B0-L3 使用三个。最大运行请求数固定为八条，模型、适配器、轨迹、预热与 SLO 相同。

这项比较回答「若可以多留一个名额，原版容量方案与两名额的调度改动哪一个在该负载表现更合适」。两个组的策略和容量同时变化，单变量影响仍参考之前的 B0 两名额/三名额和 B3 阈值对照。按本轮 B3-5s 为基线核对三项门槛，合并冷门排队 P95 至少降低 20%，热门排队 P95 增量不超过 1 秒，Goodput 降幅不超过 5%。

```bash
~/work/vllm-lora-admission/.venv/bin/python -m bench.run_g3 \
  results/g3/capacity-policy-replay --config configs/g3-capacity-vs-policy.json
python3 -m bench.analyze_g3 results/g3/capacity-policy-replay
python3 -m bench.analyze_capacity results/g3/capacity-policy-replay
python -m bench.plot_g3 results/g3/capacity-policy-replay
```

## 结果

六轮共 288 条请求，全部在 36 秒窗口内完成，无超时、未准入或抢占。三名额 B0 的调度日志观测到第三种 LoRA 真正加入活跃集合 18 次，C、D 各 9 次。

| 种子 | C/D 合并 P95，两名额 B3 → 三名额 B0 | 热门 P95，两名额 B3 → 三名额 B0 | Goodput | 忙时输出 token/s，两名额 B3 → 三名额 B0 |
|---:|---:|---:|---:|---:|
| 11443 | 5.94 → 6.15 s（+0.20 s） | 7.89 → 4.25 s | 持平 | 106.1 → 115.4 |
| 12611 | 5.73 → 6.24 s（+0.52 s） | 7.62 → 4.76 s | 持平 | 110.5 → 120.9 |
| 13723 | 9.15 → 6.13 s（−3.02 s） | 7.20 → 4.69 s | 持平 | 115.9 → 126.8 |

三名额 B0 热门排队 P95 的配对中位改善为 2.86 秒，忙时输出速率的配对中位增幅约 9.5%。各轮均有 24 条达标，Goodput 约 0.667 条/秒。冷门 P95 的绝对配对中位变化为 +0.20 秒。三项门槛同时满足的配对为 1/3，原因是前两组冷门 P95 略有上升。种子 13723 的两名额 B3 有一波未触发后续冷门优先，D 的队尾明显变慢，应结合逐请求事件阅读。

三名额组 KV 启动容量均从 43,904 降到 43,808 token。使用了同样的显存预算，整卡采样还含其他进程影响。两套配置同时改变了名额和策略，吞吐与排队差值描述的是配置级对照。若工作负载更在意热门尾延迟或忙时吞吐，本轮数据支持在资源允许时优先考虑三名额 B0。若目标是每个种子中都进一步降低冷门 P95，本轮结果并不支持统一替换。原始运行、逐次第三名额准入、配对结果与图表位于 `results/g3/capacity-vs-policy-01/`。
