# 三分钟讲解

**0:00–0:40｜发现问题。** 我用单张 RTX 5070 跑 vLLM、Qwen3-0.6B 和四个 LoRA。vLLM 有活跃适配器种类上限。如果两个名额已被 A/B 占满，新的 A/B 请求还能复用现有种类，C 则可能排在队列里很久。我给调度器加了按请求 ID 关联的事件，让每条请求从入队、因 LoRA 上限跳过到实际准入都能对上。固定轨迹三次复现 C 的长等待，放宽到四种后，C 的 LoRA 上限跳过变成零。

**0:40–1:20｜比较干预。** 我实现了排空和定向交接。在构造的竞争轨迹里，定向交接兑现了 9 次准入，冷门合并 P95 的配对中位降幅为 5.7%。我继续验证了原版扩容。`max_loras=2` 改成 3 后，在三种和四种适配器的持续流量中，九个配对的 Goodput 都提高。代价是启动 KV Cache 容量少 96 token。冷门 P95 并没有在每个种子都降低，所以我又检查了具体是谁在等。

**1:20–2:35｜用消融解释原因。** 看首页的时间线。每条线是一个请求等准入的时间，灰色只包括最早四条。我把开头从 ABCD 换成 CDAB，从第 5 条起连 LoRA 标签都逐条相同。两名额下，第一次填满的集合从 A/B 换成 C/D。用三个种子配对，只算后面的 60 条，热门 P95 配对中位增加 14.34 秒，冷门降低 3.10 秒。三名额下变化方向相同，热门增量约 1.70 秒。在其中一个种子里，同一条第 62 条 B 请求从等 0.24 秒变成等 9.60 秒。这个对照说明，最初的准入状态会影响很晚才到的相同请求。

**2:35–3:00｜给出结论和边界。** 现在推荐三名额 B0，主要因为它在所测的持续负载上提高了达标吞吐，实验策略则保留用来比较尾延迟的权衡。初始顺序影响冷热两组的等待分布，最慢的具体 LoRA 随种子变化。结果来自单卡和合成适配器，仓库同时提供可直接复算的日志归档与一组 GPU 复跑入口。
