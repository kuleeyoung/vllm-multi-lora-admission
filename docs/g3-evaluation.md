# G3 正式评估

配置在首轮启动前锁定。评估种子为 713、907、1217。每个种子使用确定性到达间隔、轻微时间抖动、适配器轮转起点及短提示词组合。相同场景和种子在 B0、B1、B2 共用轨迹。模式启动顺序按种子轮换。每个服务依次用 A/B/C/D 各一次 24 token 请求预热。

| 场景 | 到达速率 | 生成 token 上限 | 请求构成 |
|---|---:|---:|---|
| uniform-low-short | 2.0 条/秒 | 24 | A、B、C、D 均匀 |
| hot-near-short | 3.0 条/秒 | 24 | A/B 占约 75%，C/D 占约 25% |
| hot-near-long | 3.0 条/秒 | 64 | 同上 |
| hot-overload-long | 4.5 条/秒 | 64 | 同上 |

场景名表示预设的负载档位。实际接近饱和或过载程度结合客户端完成时间、批次填充和吞吐解释。每轮连续发包 6 秒，并从发包窗口起点计算固定 18 秒测量窗口。Goodput 统计该窗口内完整结束且 TTFT ≤ 2 秒、TPOT ≤ 120 ms 的请求数，再除以 18 秒。客户端请求超时为 24 秒，失败、超时、未准入分别保留。使用手动指定的生成上限和 `ignore_eos=true` 固定输出工作量。

排队使用调度进程入队至首次准入的时间差。TTFT 从客户端发送至收到首个 token ID，TPOT 用末 token 与首 token 的接收时间差除以其余 token 数。正式组记录生命周期与策略事件，每 32 次调度采一次批大小和调度耗时。批次填充率是调度到的请求数与配置上限的比值，GPU 利用率和显存是 nvidia-smi 的整卡采样。G1/G2 的详细逐轮事件保留用于归因。

主评估为 B2 对 B1。每对种子比较 C/D 合并的排队 P95 并报告分适配器结果。在 B1 事件显示名额被其他请求先占用的配对上，目标为 P95 下降 ≥ 20%，整体 Goodput 下降 ≤ 5%。均匀低负载也使用 C/D 标签检查额外开销，此时它们与 A/B 同频。小样本尾分位只用于描述这次评估。

在 WSL 项目目录用已安装的独立环境运行，结果目录须为新目录。

```bash
~/work/vllm-lora-admission/.venv/bin/python -m bench.run_g3 results/g3/replay-001
python3 -m bench.analyze_g3 results/g3/replay-001
```

图表使用安装了 Matplotlib 的 Python 运行 `python -m bench.plot_g3 results/g3/replay-001`。分析保留各轮的原始记录、轨迹哈希、聚合 CSV 和配对明细。

干净环境复跑用 `scripts/replay_g3_clean.sh "$HOME/work/vllm-lora-clean-01" results/g3/clean-01`。脚本新建 Python 环境，按依赖快照安装，核对 `pip check` 和 `pip freeze`，引用同一份已锁定的模型及适配器，在 seed 713 和长输出高负载上复跑 B0/B1/B2。

## 配对结果与结论

四个场景、三个配对种子和三种模式共 36 个运行，675 条请求全部完成，无超时、未准入或上游抢占。相同场景和种子的三个轨迹文件哈希一致。客户端最大发包滞后 4.97 ms。冻结配置 SHA256 为 `60b8e2e59cc2d5b7993be4c9fd47145ce933e19a922e2ff720df2df770871558`。

下表为各场景三个**配对差值**的中位数。负的排队差值表示后者等待更短。Goodput 比例正值表示后者下降。

| 场景 | B1 − B0 冷门 P95 | B2 − B1 冷门 P95 | B2 相对 B1 冷门 P95 降幅 | B2 相对 B1 Goodput 降幅 | B1 名额竞争配对数 |
|---|---:|---:|---:|---:|---:|
| 均匀低负载、短输出 | −27.1 ms | +35.4 ms | −38.3% | 0% | 0/3 |
| A/B 为主、短输出 | −196.7 ms | −510.1 ms | +42.6% | 0% | 0/3 |
| A/B 为主、长输出 | −1269.6 ms | +331.7 ms | −6.7% | +15.4% | 0/3 |
| A/B 为主、高负载长输出 | −2610.1 ms | +60.6 ms | −1.4% | 0% | 0/3 |

B1 在两类长输出场景均使冷门排队 P95 相比 B0 下降，不过其中一类长输出的配对 Goodput 中位降幅为 7.1%，B1 的冷热权衡仍需按负载衡量。B2 在短输出热点负载上三对中两对更快，长输出场景缺少稳定增量。两类长输出中，较低到达率一组的热门 P95 中位数由 B1 的 2.94 秒增至 B2 的 3.93 秒。高负载长输出组的批次填充中位数由 67.5% 降至 61.4%，客户端最后完成时间中位数由 12.25 秒增至 12.53 秒。18 秒窗口内各模式均完成同量输出工作，因此还保留了从计划起点到最后完成的实际跨度及对应 token/s。

正式负载的 12 个 B1 运行均未观察到其他适配器先占满释放名额。G2 的短轨迹提供了发生竞争时的交接机制证据，本次 G3 对预定的「冷门 P95 降至少 20%、Goodput 损失不超过 5%」条件没有合格样本。当前保留 B0 默认，B1/B2 作为实验开关。后续评估应单独构造带竞争的独立负载，并在多配对种子下评估其他请求的代价。

后续已完成 [突发竞争补充实验](g3-competition.md)。三个配对均复现了 B1 错失名额，B2 成功保护目标 C。合并冷门 P95 的配对中位降幅为 5.7%，Goodput 持平，未同时达到两项门槛。

每个场景每轮的冷门样本为 4–7 条，P95 和 P99 为描述性结果。整卡显存和 GPU 利用率采样包含桌面进程影响，调度耗时采样也较稀，原值保留在 `runs.csv`。排队计时起点是 EngineCore 入队，HTTP 前端解析和分词耗时包含在 TTFT 中。A/B/C/D 分组结果见 `cohorts.csv`，逐种子绝对差值和相对变化见 `pairs.csv`，原始数据和图表位于 `results/g3/paired-01/`。

## 干净环境复跑

使用新的 WSL Python 环境重新安装全部依赖。`pip check` 通过，依赖快照 SHA256 与原环境完全一致。复跑的三种模式共 81 条请求全部完成，轨迹哈希与正式组 seed 713 对应场景一致。B0、B1、B2 的冷门排队 P95 分别为 6.62、4.83、5.10 秒，满足 SLO 的请求为 14、17、15 条。正式对应组分别为 6.70、4.03、5.02 秒和 14、16、15 条。两轮方向一致：B1 降低了冷门排队，B2 相对 B1 的排队和 Goodput 均变差。复跑只执行选中的场景，采用相同的四适配器预热并复用锁定模型、适配器文件和主机级缓存。数据位于 `results/g3/clean-01/`，单个种子的复跑用于核对可重复性。
