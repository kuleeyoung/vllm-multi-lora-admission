# 2026-11-19 服务耐久与停服诊断教学索引

延续 [11 月 18 日开发归档](learning-2026-11-18.md)。本次从已选定的服务入口出发，练习如何区分功能通过、连续流量稳定、进程退出和操作系统资源清理。

| 阅读顺序 | 代码 | 要跟的真实证据 |
|---|---|---|
| 1. 启动和负载 | [serve.sh](../scripts/serve.sh)、[serving-endurance.json](../configs/serving-endurance.json)、[validate_serving.py](../bench/validate_serving.py) 的 `main` | 跟推荐档与回退档的 API/EngineCore PID，核对 3/2 名额和请求轨迹哈希 |
| 2. 每轮数据 | [validate_serving.py](../bench/validate_serving.py) 的 `summarize`、`idle_sample`、`shm_entries` | 从逐请求 JSONL 手算一轮 TTFT/TPOT 与达标数，再区分整卡 GPU 用量、进程 RSS 和打开的文件描述符 |
| 3. 中期趋势 | [analyze_endurance.py](../bench/analyze_endurance.py) 的 `span`、`plot` | 把首轮升高与后续趋势分开，明确可观察的范围 |
| 4. 停服对照及定位 | [probe_semaphore_origin.py](../bench/probe_semaphore_origin.py) 的 `HOOK` 与 `main`、本机 Python 的 `multiprocessing/resource_tracker.py` | 读 register/unregister 的调用路径，确认告警出现时是否有生成请求，检查名字是否在停服后仍可见 |

自检：资源跟踪器提示一个 semaphore「to clean up」，能否直接判定服务每轮都在泄漏？参考答案：先看它是不是退出时仍在注册表里的资源，再看清理后对象是否实际残留；要判定运行中持续增长，还要对照轮间 RSS、文件描述符和对象数量。

完整实验报告与复跑入口见 [耐久运行与停服资源检查](serving-endurance.md)。

复习顺序建议从 `results/serving/option-a-endurance-01/idle-samples.csv` 的第 1 轮和第 12 轮开始，再看 `results/serving/semaphore-origin-01/semaphore-events.jsonl`。其中一个 vLLM 工作锁在初始化时登记后注销。剩下的 tqdm 锁在退出时触发资源跟踪器清理，两条调用路径可逐行对照。当天归档为 `results/archive/vllm-multi-lora-2026-11-19-endurance.zip`。
